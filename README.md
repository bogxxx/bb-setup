# bb-setup

My [bb](https://getbb.app) setup: my own plugins, skills, agent instructions, Claude Code role agents, the installed plugin list and plugin settings.

Companion to [ai-agents-setup](https://github.com/bogxxx/ai-agents-setup), which holds the Copilot and Cursor agents.

## What's here

| Path | What | How bb uses it |
|---|---|---|
| `plugins/bb-plugin-role-picker` | Composer Role control (regular / orchestrator) and the `role_choice` tool | git source, update with `bb plugin update role-picker` |
| `plugins/bb-plugin-claude-subagents` | Subagents panel and `bb claude-subagents` | bb runs it from here (`path:` source) |
| `skills/provider-orchestration` | User skill that routes work to role agents | junction from `~/.bb/skills/provider-orchestration` |
| `skills/onboard-bb-machine` | User skill that enrolls a new machine with the bb server, sets up Copilot and the desktop app, and checks that chats work | junction from `~/.bb/skills/onboard-bb-machine` |
| `skills/copilot-troubleshoot` | User skill that diagnoses and fixes GitHub Copilot in bb (CLI, copilot-acp launcher, model list, fail-closed hooks, model pins); `scripts/check.sh` runs the read-only checks | junction from `~/.bb/skills/copilot-troubleshoot` |
| `claude/agents/` | Claude Code `orchestrator`, `explorer`, `planner`, `worker` | junction from `~/.claude/agents` |
| `claude/CLAUDE.md` | Global Claude Code instructions | copied to and from `~/.claude/CLAUDE.md` |
| `bb/AGENTS.md` | Instructions bb adds to every thread | copied to and from `~/.bb/AGENTS.md` |
| `bb/bin/copilot-acp.mjs` | Copilot ACP launcher and model lister for bb, macOS and Windows (see below) | run from the repo by the shims |
| `bb/bin/copilot-acp` | macOS shim for the launcher | symlinked from `~/.local/bin/copilot-acp` |
| `bb/bin/copilot-acp.cmd` | Windows shim for the launcher | copied to and from `~/.local/bin/` |
| `bb/bin/bb` | POSIX wrapper for the bb CLI. A non-executable `BB_CLI` runs under `node`, then the installed machine CLI | symlinked from `~/.local/bin/bb` |
| `docs/upstream/bb-cli-reexec-eacces.md` | Upstream report: bare `bb` exits 0 when `BB_CLI` is not executable | kept until bb ships a fix |
| `bb/plugins.json` | Installed plugins (git, npm, local) and builtin on/off state | generated by `sync.ps1` |
| `bb/plugin-settings.json` | Plugin settings that differ from the defaults (secret fields are left out) | generated by `sync.ps1` |

Folders are live: editing them here changes what bb and Claude use right away. Windows can't link single files without admin rights, so single files are copied, and the newer copy wins.

## Make a change

1. Edit it. Plugins, skills and agents can be edited in this repo. `AGENTS.md`, `CLAUDE.md` and the launcher can be edited in either place. Settings and installs go through the bb app or `bb plugin ...`.
2. For plugin code, rebuild and reload: `bb plugin dev plugins/<name>` watches and reloads, or run `bb plugin build plugins/<name>` and then `bb plugin reload <id>`.
3. Save it to GitHub:

   ```powershell
   .\scripts\sync.ps1 -m "What changed"
   ```

   This copies the files, exports the plugin list and settings, then commits and pushes. `-DryRun` pulls, copies and links nothing and writes nothing to the repo: it prints the diffs of `bb/plugins.json` and `bb/plugin-settings.json` against the committed files and commits nothing. `-NoPush` commits without pushing.

`~/.bb/AGENTS.md` tells every bb agent to run `sync.ps1` after it changes the setup, so agent changes reach GitHub too.

### New plugin

```powershell
cd $HOME\src\bb-setup\plugins
bb plugin new my-thing          # creates bb-plugin-my-thing
cd bb-plugin-my-thing; npm install; bb plugin build
bb plugin install $PWD --yes
..\..\scripts\sync.ps1 -m "Add my-thing plugin"
```

## Set up a new machine

Install bb, git, Node.js and gh, start bb, then run:

```powershell
git clone https://github.com/bogxxx/bb-setup $HOME\src\bb-setup
& $HOME\src\bb-setup\scripts\install.ps1
```

It links the folders, copies the files, builds and installs the local plugins, installs the git and npm plugins, clones local plugins that have a git remote (such as `burn`), matches the builtin on/off state and applies the settings. You can run it again safely.

Not included: plugin secrets, bb account sign-in, gh and provider logins, `bb.db`, and thread data. Set those up by hand. The Copilot agent in `provider-acp.customAgents` runs the bare command `copilot-acp`, so `~/.local/bin` must be on PATH; the launcher runs `bb/bin/copilot-acp.mjs` from `~/src/bb-setup`.

### Add a machine to the bogxxx.getbb.app server

A machine that only runs threads for the remote server (no local bb server) is enrolled with the server's install command, not set up with the full `install.ps1`. The `onboard-bb-machine` skill (`skills/onboard-bb-machine/SKILL.md`) has the steps and the known failures. In short:

1. Run the server's enrollment command once (the `bbde_` token is single-use; on Windows use `install.ps1` with the same token). If Windows refuses to start the daemon through WMI, start `install-machine-windows.mjs --run` by hand.
2. Install Copilot with `winget install GitHub.Copilot` (the launcher looks for `copilot.exe`; npm only installs `copilot.cmd`), then `copilot login`.
3. Back up `~/.copilot/agents` and the other copied files, then run `install.ps1 -SkipPlugins -SkipSettings`. Plugins and settings already live on the server, and the `bb` CLI of an enrolled-only machine gets `HTTP 401`.
4. Put `~/.local/bin` first on the user PATH, remove any other `copilot-acp` wrapper, and restart the host daemon.
5. In the bb app, select the machine and "GitHub Copilot". The model picker shows context sizes (for example "Claude Opus 5.5 1M").

## macOS

```bash
T=$(gh auth token --user bogxxx)
git clone https://x-access-token:$T@github.com/bogxxx/bb-setup ~/src/bb-setup
git -C ~/src/bb-setup remote set-url origin https://github.com/bogxxx/bb-setup
~/src/bb-setup/scripts/sync.sh -m "What changed"
```

In shells, run bb as `node "$BB_CLI"` so the CLI still runs when `$BB_CLI` is not executable (see [docs/upstream/bb-cli-reexec-eacces.md](docs/upstream/bb-cli-reexec-eacces.md)).

`scripts/sync.sh` is the macOS counterpart of `sync.ps1`. Its first run is the install. It pulls first, then symlinks `~/.bb/skills/provider-orchestration`, `~/.claude/agents`, `~/.bb/AGENTS.md`, `~/.claude/CLAUDE.md`, `~/.local/bin/bb` (`bb/bin/bb`) and `~/.local/bin/copilot-acp` into the repo. macOS can link single files, so nothing is copied. Existing files are moved to `*.bak-<timestamp>`, and a local file that is newer than the repo copy is copied into the repo first. It then runs `chmod +x` on a non-executable `BB_CLI` and on each `~/.bb-machines/*/npm/lib/node_modules/bb-app/host-daemon/dist/bb`. `bb/bin/bb` runs a non-executable `BB_CLI` under `node`. The upstream report is [docs/upstream/bb-cli-reexec-eacces.md](docs/upstream/bb-cli-reexec-eacces.md). Then it commits and pushes. Options: `-m`, `--dry-run`, `--no-push`, `--no-plugins`.

Plugins and plugin settings are exported from the bb server the CLI is connected to, whether it runs on this Mac, on another host, or on Windows. The script detects a local server by checking that the server's data dir exists on this machine. For a remote server, a `path:` plugin's directory is not on this machine, so its source is kept as the server reports it and not probed locally. `--no-plugins` skips the export.

The script runs bb through `BB_CLI` (the bb entry point; a non-executable one runs under `node`), not bare `bb` on PATH. A bb command that fails or prints nothing stops the script before anything is committed, so `bb/plugins.json` and `bb/plugin-settings.json` are never written partially or with dropped fields. `--dry-run` pulls nothing, links nothing, and writes nothing to the repo or home folder. It prints the diffs of `bb/plugins.json` and `bb/plugin-settings.json` against the committed files and commits nothing.

Git pulls and pushes use the `bogxxx` gh account's token for that one command. The script never runs `gh auth switch`, because bb's Copilot integration depends on the active gh account. Set `BB_SETUP_GH_USER` to use another account.

## Copilot context window

bb switches an ACP session's model with `session/set_config_option`, and Copilot resets the context window to the model's standard tier (200k for Claude Opus 5.5) on every switch. Copilot's ACP server always starts on Claude Sonnet 5.5, so almost every bb thread lost the long tier. The `provider-acp.customAgents` entry for Copilot avoids the switch. It runs `copilot-acp` with `modelCli` (`listArgs: ["--list-models"]`, `selectFlag: "--model"`), so bb launches Copilot on the thread's model, and restarts and reloads the session when the model changes.

There is one "GitHub Copilot" agent, and the context window is chosen in its model picker. A model with a long tier is listed twice, for example "Claude Opus 5.5 (1M)" and "Claude Opus 5.5 (200k)". Models without one, such as GPT-5.3-Codex, are listed once.

- `copilot-acp --list-models` asks Copilot for its models, the reasoning efforts of each (ACP) and their context tiers (`copilot --headless`, `models.list`). It prints one line per model, tier and effort, such as `claude-opus-5.5-high` and `claude-opus-5.5-standard-high`. The list is cached for a day in `~/.cache/bb-copilot-acp/models-v2.txt`; `--refresh` reprobes.
- `copilot-acp --model claude-opus-5.5-high` runs `copilot --acp --model claude-opus-5.5 --reasoning-effort high --context long_context`. The `-standard` ids run `--context default`. `--print-args` shows the arguments without starting Copilot.
- Copilot gets the token of the gh account `bohdan-krechko-akerbp` (override with `COPILOT_GH_USER`), whichever gh account is active. `COPILOT_BIN` overrides the Copilot path.
- The same `copilot-acp` command works on every machine: on macOS `~/.local/bin/copilot-acp` links to the bash shim, and on Windows `%USERPROFILE%\.local\bin\copilot-acp.cmd` runs the launcher with `node`.
